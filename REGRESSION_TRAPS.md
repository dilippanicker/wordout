# Regression Traps

Resolved-incident write-ups and historical reasoning for closed decisions, extracted from CLAUDE.md to keep that file within its ~300-line soft budget. CLAUDE.md links here with "see REGRESSION_TRAPS.md" wherever the current behavior depends on one of these. Read the linked CLAUDE.md section first for the active spec — this file is the "why", not the spec itself.

## Daily word selection collision (fixed v1.5.8)
Word indices were previously derived via a bit-masked/bit-shifted formula from the UTC-midnight seed (`Math.imul(dayMs, 2654435761)`), which collided roughly 8 days per decade and capped indices at 2047 — words beyond that index in the answer list could never be selected as a daily word. Fixed by switching to `dailyIndices(dayNum, n)`, a mulberry32 PRNG sampled with reject-duplicate across the full `[0, n)` range. No cutover-date gating was needed for the fix: `dailyAnswers` is computed once per day and persisted, so an in-progress day keeps its already-computed word (old or new algorithm) and only future days see the new derivation — same-day cross-version consistency was never a requirement here (no historical word display, share text never reveals the word).

## Daily day-boundary local-time bug (fixed)
`getTodayString()`/`getYesterdayString()` and the countdown (`msUntilMidnight()`) previously used local time. For any timezone ahead of UTC (e.g. IST +5:30), local midnight arrives before real UTC midnight, so `checkAndReset()` fired early during that gap and the freshly-reset game reused `getDailyAnswers()`'s still-previous-UTC-day word — the daily word appeared to repeat across two consecutive local days. Fixed by keying all date logic off UTC date components. Regression test: `__tests__/store-invariants.test.ts` "day boundary is UTC, not local" (sets `TZ=Asia/Kolkata`, fails against the pre-fix local-time implementation).

## Quordle fresh-board difficulty switch (fixed v1.5.9, superseded v1.7.2)
The fresh-board (no guesses yet) path in `handleDifficultyToggle()` skipped the `newGame()` call after `setDifficulty()`, so the board kept the old difficulty's row count until a manual New Game — because `quordleStore.maxGuesses` (and thus rendered row count) is only recomputed inside `newGame()`, not derived live like single-board's. Fixed at the time by making both the confirmAbandon path and the fresh-board path call `useQuordleStore.getState().newGame()` unconditionally after `setDifficulty()`.

That "always call `newGame()`" fix quietly became the v1.7.1 "locked" decision that a *completed* quordle board also advances straight to the next difficulty with a fresh board — because `newGame()` deletes whatever snapshot exists for the current board count with no save step first, there was no way to distinguish "fresh board, needs a maxGuesses refresh" from "finished board, about to be thrown away." A user reported this as a bug in v1.7.2: finishing Easy, switching to Hard, then back to Easy showed a brand-new board instead of the one just finished — unlike single-board practice, which already preserved per-difficulty state via `gameStore.switchDifficulty`. Root cause: `quordleStore.snapshots` was keyed only by board count, so there was no dimension to hold "easy 2-out" and "hard 2-out" state simultaneously.

Fixed in v1.7.2 by adding `quordleStore.switchDifficulty(newDifficulty)`, keyed by `` `${difficulty}-${boardCount}` `` (see `snapshotKey()`), mirroring `gameStore.switchDifficulty`'s save-then-restore-or-fresh pattern instead of `newGame()`'s unconditional wipe. This preserves the original v1.5.9 fix's requirement (`maxGuesses` must be freshly correct on every switch) without losing finished-board data: `switchDifficulty`'s fresh-board branch computes `maxGuesses` explicitly via `maxGuessesForDifficulty(newDifficulty, boardCount)` — not via `initialState()`, which reads difficulty from settingsStore and would still see the *outgoing* difficulty, since `switchDifficulty(next)` must run **before** `setDifficulty(next)` (same ordering single-board already required) so the save step captures the outgoing difficulty's key correctly.

## Language switch wiped the other language's board (fixed)
`gameStore` and `quordleStore` both treated any language change as a full reset — the module-level `settingsStore.subscribe` called `newGame()` (single-board) or set `snapshots: {}` outright (quordle) instead of snapshotting. Same underlying pattern as the fresh-board difficulty switch entry above, but for language: a user finishing a 2-out board, switching `en_gb`→`en_us`, then back to `en_gb` saw a blank board instead of the finished one.

Fixed by extending both stores' snapshot keys to include language (`quordleStore`: `` `${language}-${difficulty}-${boardCount}` ``, `gameStore`: `` `${language}-${difficulty}` ``) and adding `switchLanguage(oldLanguage, newLanguage)` to each, mirroring `switchDifficulty`'s save-then-restore-or-fresh pattern.

Unlike difficulty/board-count, nothing calls `switchLanguage` directly from UI code — `setLanguage()` is called straight from the header flag tap / Settings picker, and the `settingsStore.subscribe` callback reacts to it, since that callback is the only place both the old (`prev.language`) and new (`curr.language`) values are available together (Zustand subscribers fire *after* the store has already committed the new value). **Test gotcha**: any test exercising this must call `useSettingsStore.setState({ language })` only. Calling `switchLanguage()` manually *and* relying on the setState to also fire the subscribe double-applies the switch and silently corrupts the round-trip — caught during development by tracing snapshot keys, not by the test's assertions alone.

`butler push` commands targeted `dilippanicker/wordout` for several sessions before being caught — the actual itch.io account is `onglipo`, a different identity from the GitHub repo owner and Google Play package name. Any butler command must target `onglipo/wordout:<channel>`.

## broth.itch.ovh retired (fixed)
The butler download domain `broth.itch.ovh` used in earlier drafts is retired and no longer resolves — itch.io moved to `broth.itch.zone`. This wasn't a typo; itch.io actually decommissioned the old domain. A stale `.ovh` reference fails with `curl: (6) Could not resolve host`, which isn't obviously itch.io-related from the error alone.

## itch.io HTML5 routing (fixed)
Expo Router has no supported hash-based or dynamic-subpath routing (confirmed by reading the installed `expo-router` source and cross-checking upstream: [expo/expo#27163](https://github.com/expo/expo/issues/27163), [expo/router#165](https://github.com/expo/router/issues/165)), and itch.io assigns a new CDN path on every upload with no stable prefix to hardcode — so the router 404s before the app boots. Fixed without touching app code: `scripts/itchio-postprocess.py` injects a boot-time `<script>` into the exported `index.html` that pins an explicit `<base href>` to the real (unknown-until-runtime) CDN directory — so relative asset loads stay correctly anchored — and *then* normalizes `window.location` to `/` via `history.replaceState()` so Expo Router's initial route match succeeds. Order matters: doing the `replaceState()` first (the obvious first attempt) breaks asset loading instead, because it also moves `document.baseURI`, which relative references resolve against. Verified locally against a simulated nested CDN path (clean boot, correct asset loads, round-trip client-side navigation to Settings and back), then verified again live including actually playing a guess in the production embed.

## itch.io embed sizing (fixed, twice)
The itch.io project embed was first set to 390×844 (default), then widened to 430×844 to "match the app's design width" — both were wrong. An iframe sized to *exactly* match the 430×932 web card leaves zero slack for the dark-backdrop framing to render, so the game filled the iframe edge-to-edge with no visible boundary against the surrounding page. "Fixed" by widening to 700×1050, plus enabling the "fullscreen button" option — this in turn broke worse: itch.io has no responsive/auto-fit sizing for non-Unity HTML5 games (checked live on the Edit Game page — the only options are "Manually set size" or "Auto-detect, Unity only"), so a fixed 1050px-tall iframe routinely exceeded real laptop browser viewports, forcing the *surrounding itch.io page* to scroll before the keyboard was reachable. Also made the dark backdrop itself look bad (too much empty frame). Settled on 430×820 (both dimensions at or under the app's own 430×932 web-card cap, so the embed always renders full-bleed/no-frame) plus a theme-matched 1px border drawn in `app/_layout.tsx`'s `webCard` style — the border gives a visible boundary without needing the container to be oversized, which is what let the size come back down without reintroducing the original "no visible boundary" complaint.

## Keyboard Enter key glyph (fixed v1.5.5→v1.5.6)
v1.5.5 changed the Enter key's functional value to the glyph `'⏎'` directly, which broke submit — the glyph got typed as a literal character instead of triggering submit. Fixed in v1.5.6 by keeping the internal value always `'ENTER'` and mapping to the display glyph only at render time (`Text` content), so `onKey`/`keyStatuses` lookups keyed on `'ENTER'` stay correct.

## itch.io fullscreen detection via document.fullscreenElement (fixed)
First attempt at clearing the stats-icon/fullscreen-button overlap tried tracking `document.fullscreenElement` inside our own document, on the theory that itch's iframe has `allowfullscreen` so its fullscreen state should cascade down into nested browsing contexts per the Fullscreen API spec. Confirmed live that it doesn't fire in practice — the reserved padding stayed even after entering itch's actual fullscreen (either itch's fullscreen button doesn't use `requestFullscreen()` at all, or the permission doesn't propagate as expected for this cross-origin embed). Replaced with a `useWindowDimensions()` check instead: only reserve the clearance while the viewport is still at or under the web-card cap (430×932), since that's the only state where our card is genuinely edge-to-edge and shares a corner with itch's button — real fullscreen expands the iframe past the cap, so the card reverts to its normal backdropped look regardless of what itch's button actually does.

## Review request double-fire on tap near the 5s auto-dismiss (fixed v1.9.1)
A tap on the end-game overlay at ~4.68–5.0s ran `dismissEndGame` once from the tap, then again from the still-live 5s auto-dismiss timer (the timer is only cleared when the 320ms fade finishes hiding the overlay). Both scheduled a review request; `recordReviewPrompt` only runs after `requestReview` resolves, so both could pass the eligibility check. Fixed with a per-win `{current:boolean}` flag passed into `scheduleReviewAfterWin` (held as `reviewScheduledRef` in the component, reset on `'playing'`). The flag is a parameter, not hidden inside the component, so the double-dismiss case is unit-testable without rendering `index.tsx`. The 1500ms and 320ms timers themselves are deliberately uncancellable (starting a new game right after a tap still lets the request fire).

## Pages root is deployed from docs/ (v1.9.1 session)
Before this, no workflow deployed `docs/` — the landing page and privacy policy on the gh-pages root were hand-seeded, so a `docs/index.html` edit never went live. `deploy-web.yml` now publishes `docs/` to the root with `keep_files: true` right after the `/play/` deploy (same job, so the two gh-pages pushes cannot race; every deploy step must keep `keep_files: true` or one will delete the other's files).

## Web dev server shows a stale app version (stale Metro cache)
On web, `Constants.expoConfig` comes from `process.env.APP_MANIFEST`, inlined by Metro at transform time (`expo-constants/build/ExponentConstants.web.js`). After bumping `app.json`, the dev server kept serving the old value (Settings showed v1.8.1 with `app.json` at 1.9.0). Restarting with `npx expo start --web --clear` fixed it (then showed v1.9.1). Not an app bug and native builds are unaffected; the exact cached file wasn't pinned down. If a web version string looks wrong, `--clear` before debugging.

## Distribution (full)

- **Web (GitHub Pages):** automated — `deploy-web.yml` (push to main) and `build-apk.yml`'s `deploy-web` job (after a manual build) both export and deploy to the `gh-pages` branch, under `/play/` so the existing landing page + Play Store privacy policy at the Pages root are untouched (`keep_files: true`).
- **Card sizing / letterboxing (`constants/layout.ts`, `app/_layout.tsx`):** on web (always) and native large screens (≥600dp smallest dimension — Android 16+ ignores our portrait lock there since targetSdk is 36), the game renders as a fixed-size card (`WEB_CARD_MAX_WIDTH` 430 / `WEB_CARD_MAX_HEIGHT` 932 — iPhone 14 Pro Max's logical size, chosen to sit just above the tallest realistic phone viewport so it never clips real mobile users) centered on a `#1a1a1a` backdrop, instead of stretching full window size. The gate is `shouldLetterbox(w, h)` — the **single source of truth used by both `_layout.tsx` (card styling) and `index.tsx` (screenW/screenH clamps)**; never re-derive the condition locally or the two go out of sync (boards overflow, paging offsets misalign). Native phones (< 600dp min dimension) are provably unaffected — they keep plain `flex:1` full-bleed. Regression tests: `__tests__/layout.test.ts`. Below the cap (any real phone-sized web window, or an undersized iframe like itch.io's — see below), the clamps are a no-op — the card instead draws a theme-matched 1px border so there's still a visible edge against the surrounding page with no dark backdrop space required (also needed on native tablets in dark theme, where card `#121213` barely contrasts with the `#1a1a1a` backdrop and RN shadow doesn't render on Android). Native-tablet rendering is web-verified only (same code path), not device-verified.
- **itch.io project:** `onglipo/wordout` (https://onglipo.itch.io/wordout) — **the itch.io account is `onglipo`, not `dilippanicker`** (unlike the GitHub repo and Google Play package name). `butler push` targets must use `onglipo/wordout:<channel>`. See REGRESSION_TRAPS.md — this was silently wrong for several sessions before being caught.
- **itch.io — Android (APK):** automated — `build-apk.yml` pushes `./wordout.apk` via `butler` to the `:android` channel after every build (`ITCHIO_API_KEY` secret). Butler installs from `https://broth.itch.zone/...` — **not `.ovh`, which is retired and no longer resolves** (see REGRESSION_TRAPS.md). Never manually `butler push` a locally-named file (e.g. from `releases/`) straight to this channel — butler names the itch.io download after the local file's basename, and anything other than `wordout.apk` creates a second, permanent duplicate entry the automated pipeline never updates or cleans up (found 2026-07-27: a stale `wordout-latest.apk` sitting alongside the real one — needs manual deletion on itch.io's Edit Game page).
- **itch.io — Web (HTML5):** automated — `deploy-web.yml`'s `deploy-itchio-web` job exports a *separate, root-relative* web build (baseUrl unset), post-processes it with `scripts/itchio-postprocess.py`, and pushes to the `:html5` channel via `butler`. `./make.sh deploy-web` does the same locally. It also adds `viewport-fit=cover` to the viewport meta tag (itch-export-only, not applied to the GitHub Pages export) so `env(safe-area-inset-*)` can activate on notched phones when itch's mobile-friendly embed renders full-screen — best-effort, unverified against a real notch. Kept at or below the 430×932 web card cap so the embed always renders full-bleed (no dark backdrop) — a boundary is instead drawn in code (`app/_layout.tsx`'s `webCard` border) rather than by oversizing the iframe, since itch.io has no responsive/auto-fit sizing for non-Unity HTML5 and any size taller than 932 risks forcing the surrounding itch.io page to scroll before the keyboard is reachable.
